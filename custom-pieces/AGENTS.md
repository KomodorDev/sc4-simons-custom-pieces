## 1. Agent workflow

- Write each Markdown prose paragraph on one physical source line. Let the viewer wrap; preserve structural and intentional breaks.
- Apply the [shared JSONC source convention](STRUCTURE.md#51-shared-jsonc-sources-and-strict-json-exports): keep readable title and summary comments, use the shared parser and header-preserving writers, and preserve strict JSON at machine/export boundaries. The first migration excludes individual piece and assembly records; update the four declared compatibility views from their JSONC authorities rather than authoring duplicate data.
- Follow the [shared Markdown conventions](STRUCTURE.md#4-markdown-heading-numbering-and-navigation): keep one unnumbered title, number second-level chapters from 1 and subsections as 2.1 and deeper, and provide navigation links only for second-level chapters. Preserve previous heading anchors and generator ownership. The current shared-document migration excludes piece and assembly manuals, imported material, and frozen evidence.
- Before allocating or implementing a new type, apply the [piece-versus-assembly decision](docs/WORKFLOW_PIECE_CREATION.md#1-decide-between-a-piece-and-an-assembly), even when the request calls the complete design a “piece.” Prefer reusable modules for complete complex junctions, announce the assembly delivery, and follow the assembly workflow. Model render-group packing is a separate technical check.
- Every user-requested atomization or further-splitting review includes the [required line drawing](docs/WORKFLOW_ASSEMBLY_CREATION.md#161-required-line-drawing-for-user-requested-atomization), including a finding that no further split is possible. Show actual straight and curved routes, tile coordinates, candidate cuts, decisions, and physical obstacles; retain the drawing and its evidence with the owning subject.
- For piece or assembly design, use the [piece and assembly design skill](skills/network-piece-and-assembly-design/SKILL.md) to identify task inputs, follow the selected creation workflow, and report verified outputs. If the workflow is already selected, continue it without returning to the README to select it again. Read the owning domain's `AGENTS.md` for additional constraints, and consult its `NETWORK_SPEC.md` where implemented.
- For an existing subject's prose, artwork, or connector-output refresh, start directly with [documentation generation](docs/WORKFLOW_DOCUMENTATION_GENERATION.md#1-choose-the-refresh-scope); do not repeat piece allocation or assembly design. Use the [library README](README.md) only when the task is unclear, and [STRUCTURE.md](STRUCTURE.md#21-document-names-and-reading-order) to identify the document or source that owns a rule.
- Choose new folder identifiers and readable piece or assembly names through the shared [naming conventions](docs/NAMING_CONVENTIONS.md). Preserve existing identifiers, references, and frozen evidence; a naming-policy change alone does not rename the catalogue or refresh artwork.
- Every assembly uses one menu button with Tab/Shift+Tab cycling through its reusable components. Follow the [assembly menu policy](docs/WORKFLOW_ASSEMBLY_CREATION.md#1-terms-and-evidence) and [packaging step](docs/BUILD_AND_INSTALL.md#8-prepare-the-assembly-menu); each click places one component.
- New subjects and guides deliberately migrated to the split layout use README plus TESTING. Follow the [shared six-chapter TESTING layout](docs/WORKFLOW_DOCUMENTATION_GENERATION.md#123-required-piece-and-assembly-testing-layout), with generated connections under Test scope and split-piece summaries and checks under Results and known issues. Retain legacy piece guides until deliberately migrated. Shared observation instructions live in [docs/TESTING.md](docs/TESTING.md). Do not add duplicate connection, checklist, or recording-helper Markdown pages.
- New piece guides and deliberately migrated legacy guides use the [split layout](docs/WORKFLOW_DOCUMENTATION_GENERATION.md#121-piece-readme): README has 1. Views, 2. Piece and placement, and 3. Connection matrix, with the exact navigation label `Testing ↗ (separate document)` linked to the piece’s own `TESTING.md`, matching the assembly wording. Use `<!-- PIECE README LAYOUT: 2 -->` and `<!-- PIECE TESTING LAYOUT: 1 -->`. Keep the generated matrix intrinsic to the piece’s measured journeys, with separate saved-route, Route Query, and visible-travel evidence, and link its exact cases into TESTING.md; it does not establish neighbour compatibility.
- Edit maintained prose or the generator that owns its marked section. Authoritative JSON stores definitions, placements, connections and observations; generated inventories and checkboxes are views.
- For a new subject, follow the [staged creation checklist](docs/WORKFLOW_DOCUMENTATION_GENERATION.md#3-creation-checklist-and-output-files), including its required/conditional files and exact producing commands. Use the [bounded existing-piece assembly starter](docs/WORKFLOW_ASSEMBLY_CREATION.md#12-start-a-small-hsr-assembly-from-existing-pieces) for the plan, registry, menu, and first-evidence handoff. Run `python3 -B custom-pieces/scp.py docs-check` from the repository root, or select exact subjects with repeated `--piece`/`--assembly`; it is read-only and cannot turn pending draft prose, native inputs, or unverified game cases into completed evidence.
- Keep each piece's or assembly's canonical `icon.png` beside its `piece.json` or `assembly.json`; store documentation images under that subject's `previews/`, and their provenance under `evidence/`. Follow [artwork ownership and folders](docs/WORKFLOW_DOCUMENTATION_GENERATION.md#4-artwork-ownership-and-folders) when generating or reorganizing them.
- Every new or refreshed render starts with `Assembly - ` or `Piece - ` followed by its display name. Its second row starts with the view purpose: `Clean view`, `Component guide`, `Construction view`, or `Connection overview`, as defined in the [shared caption contract](docs/WORKFLOW_DOCUMENTATION_GENERATION.md#7-assembly-picture-set-and-in-picture-identification). Keep game-test status out of captions and footers; use the subject's generated connection matrix and linked testing records. Keep the owning renderer consistent with that contract; refresh existing artwork only within the requested scope.
- Use the library-owned [connector reference](docs/CONNECTOR_METADATA.md) for source semantics and the [documentation-generation workflow](docs/WORKFLOW_DOCUMENTATION_GENERATION.md) for artwork, exports, and cards. Keep shared rules in `docs/`, network facts in the owning specification, and particular measurements with the piece or assembly. Consumer applications must use the library exports rather than duplicate source parsing. Follow the documented verification/extraction order and explicit coverage limits.
- Preserve game IDs, approved geometry and relevant evidence for retained subjects. Explicitly deleted subjects retain no retired definitions, artifacts or compatibility copies.
- Only explicit human confirmation changes manual observations. Software tests cannot tick game rendering, connection or journey cases. Preserve failed and stale results and their exact scope.
- Keep intrinsic piece validation and extraction separate from compatibility discovery, which is not supplied by the current library. Do not generate manual port/counterpart matrices or use legacy endpoint shortlists as complete-boundary matches. Any future discovery consumer must exclude unmigrated, missing, stale, or invalid connector inputs explicitly; it must not infer their compatibility or author missing metadata.
- Use [framework engineering](docs/FRAMEWORK_ENGINEERING.md) and [build/install](docs/BUILD_AND_INSTALL.md) for shared contracts. Keep one combined controller per installed selection; building, installing and publishing remain separate actions within the user's authorized scope.
